## GAME IDENTITY

Chimpions Dash is a dependency-free HTML5 Canvas endless runner. The fantasy is a chosen Chimpion helmet/head attached to a runner body, entering the jungle via a UFO claw and surviving an accelerating sequence of jump, long-jump and slide hazards while collecting bananas and building Flow. Sessions are short-to-medium endless attempts, primarily desktop browser with touch/mobile support.

The current implementation supports that identity well mechanically. The commercial gap is presentation consistency: a runner lives or dies on instant hazard readability, precise grounding and repeated high-quality sprite work. The code already has enough systems; the next gains should come from stabilizing art, animation, feedback, onboarding and visual QA rather than adding more features.

## FIRST-ACTION TECHNICAL MAP

1. **Engine / renderer:** custom dependency-free JavaScript, DOM UI + HTML5 2D Canvas.
2. **Architecture:** `engine.js` deterministic simulation, `render.js` renderer, `app.js` state/input/UI, `audio.js` sound/music, static JSON/assets.
3. **Loop:** requestAnimationFrame render with 120 Hz fixed simulation steps.
4. **Physics:** scalar vertical motion, variable jump hold, stronger falling gravity, coyote time and jump buffer.
5. **Collision:** inset AABBs, overhead standing-block safety, shield invulnerability.
6. **Spawner:** seeded weighted pattern catalog, stage-gated hazard families and explicit reaction/recovery windows.
7. **Difficulty:** 30-second stages, base 265 px/s, target curve reaching the 540 px/s cap around Stage 10.
8. **Assets:** 221 portraits, body atlas, jungle background, transparent hazard/collectible PNGs, ground, UFO and MP3.
9. **CI/CD:** deterministic engine QA + UI mock QA + GitHub Pages deployment.
10. **Primary risk:** visual assets can regress without existing tests detecting missing/opaque/corrupt gameplay sprites.

## GAMEPLAY / FEEL / BALANCE

### Strengths
- Fixed `STEP=1/120` simulation produces consistent 30–240 FPS motion in QA.
- Tap versus hold jump is deterministic and protected by coyote/buffer tests.
- Slide has a minimum duration and prevents standing up into overhead geometry.
- Pattern recovery is conservative enough for four automated ten-minute runs.
- Bananas are no longer guaranteed on every hazard; separate gap sprinkling provides between-hazard collections.
- Stage speed curve meaningfully escalates and soft-caps at 540 px/s.

### Risks / tuning
- Automated survival proves reachability, not fun. Late-stage moving overhead hazards need human playtests at keyboard and touch latency.
- The bot chooses very cleanly; human reaction windows should be measured at Stage 7–10 on 60 Hz mobile browsers.
- Flow is generous because clean passes, bananas, Perfect actions and Close Calls all contribute. Retention may improve if riskier actions are more valuable than passive survival.
- First-time tutorial invulnerability is good, but onboarding should visually demonstrate hold duration and slide timing rather than rely mainly on text hints.

## OBSTACLES / HAZARDS / COLLECTIBLES

Current active roster: fallen log, mushrooms, thorns, stump, spike, log pile, puddle, spike patch, branch, vine and canopy. The most important rule is silhouette consistency: short hazards must read as jumpable, wide hazards as commitment jumps, and overhead hazards as slide-only before they reach the player.

Stage 1 should remain visually simple: short logs/mushrooms plus the long-jump log pile. Water should begin later. Slide-only branches begin from Stage 2. This creates a clean onboarding vocabulary before combinations are introduced.

Banana generation is structurally improved: each hazard can have no bananas, low trails, medium arcs or high arcs, and gap sprinkling can place fruit between encounters. Continue tuning density by playtest rather than increasing count further.

## GRAPHICS / ART DIRECTION

The renderer now references dedicated transparent PNGs under `assets/sprites-clean/`, a separate ground PNG and UFO/claw art. This is the correct direction. The remaining issue is consistency and validation, not lack of assets.

Required art rules:
- no opaque rectangular backgrounds on gameplay sprites;
- no sprite-sheet edge bleed;
- no stretched source art;
- all feet/hazards share one visual baseline with collider debug overlays;
- background plants must never resemble pickups/hazards;
- water must read as dangerous through shape/contrast, not just blue color;
- bananas need a single unmistakable silhouette with clean alpha margins.

The current ground/hazard alignment uses a shared 12 px visual drop. Keep one shared world baseline; do not independently tweak player and hazard offsets in future patches.

## ANIMATION

The UFO arrival is state-driven and does not advance gameplay time. That is a good signature moment and should remain. The run cycle is still the largest animation limitation: the body atlas provides a small number of distinct locomotion poses. Before release, add two to four true in-between run frames and a dedicated landing recovery frame. Avoid generated frame interpolation that creates ghosting around limbs.

For water, animate subtle surface frames or UV-like sprite swaps, not large procedural waves that conflict with pixel art. Overhead moving hazards should bob slowly enough that the safe window remains readable.

## UI / UX / ACCESSIBILITY

Strengths: keyboard + mouse + touch input, 44 px minimum buttons, focus-visible styling, pause, help, collection search/favorites/random, local bests, result sharing and clear HUD separation.

Improvements:
- Add a separate Music/SFX volume split eventually; current one-button sound toggle is simple but coarse.
- Add reduced-motion behavior beyond the Flow bar for camera shake/particles/UFO movement.
- On mobile, test arena minimum height and touch controls against browser UI chrome and safe-area insets.
- Add an explicit visual “hold” tutorial meter for high jump.
- Ensure selected Chimpion head crop is reviewed across all 221 portraits; automated image presence cannot catch a bad face crop.

## AUDIO

Music lifecycle is sensible: starts from a user gesture, loops, follows sound enable, pauses and resumes around game state. Dash sound is explicitly tied to actual slide state, avoiding prior random triggering. Before release, perform listening tests for fatigue and mix hierarchy. The MP3 is the single largest asset and should be re-encoded only after the mix is approved.

## PERFORMANCE

Expected browser performance is reasonable: 2D Canvas, no framework runtime, DPR capped at 2, fixed-step loop, AABB collision and small active object counts. Main risks are:
- repeated DOM HUD writes every frame;
- many canvas primitives in weather/particles;
- all active hazard PNGs are preloaded immediately;
- 4.5 MB music on first play.

Low-effort optimization: cache last HUD text values and only update changed DOM nodes. Do this after visual stability, not during the current art-recovery phase.

## ASSET PIPELINE

The deployment contains ~15.3 MB of assets. Roughly 2.15 MB are duplicate `assets/heads/` files not used by the current collection paths, and ~3.29 MB are obvious legacy/restored atlas/ground assets. They do not all download at runtime, but they increase artifact size and increase the chance that a future patch references stale art. Remove them only after a stable release checkpoint and an automated reference audit.

## CODE / ARCHITECTURE

The current four-module split is appropriate for indie scope; a framework migration is not justified. The problem is density inside modules. Recommended incremental extraction:
- `encounters.js`: TYPES, pattern catalog, speed curve;
- `asset-manifest.js`: canonical asset paths and active/legacy status;
- `effects.js`: particles/weather only if render.js grows further.

Do not migrate to Three.js/Phaser just to improve polish. The current game is fundamentally suited to Canvas 2D.

## IF THIS WERE MY GAME

1. **Fix immediately:** visual regressions, Stage 1 vocabulary, missing/opaque assets, grounding and banana edge artifacts.
2. **Redesign:** only weak individual sprites and water animation—not the whole renderer.
3. **Keep:** deterministic engine, variable jump, slide safety, Daily Jungle, Flow, UFO identity, local-first saves.
4. **Remove:** stale duplicate assets after a stable checkpoint.
5. **Improve visually:** run animation, water, contact grounding, consistent pixel scale.
6. **Improve mechanically:** late-stage human tuning and clearer moving-hazard anticipation.
7. **Optimize:** HUD writes, music size and deploy artifact after correctness.
8. **Add before release:** screenshot regression CI, browser/device matrix, onboarding hold feedback.
9. **Postpone:** online leaderboard, accounts, economy, 3D migration and major progression meta.
10. **Largest prototype-to-commercial difference:** a locked, coherent art/animation baseline protected by real visual regression testing.

The game does not need more systems right now. It needs fewer regressions, stronger authored animation, consistent gameplay art and rigorous browser-level visual QA.
